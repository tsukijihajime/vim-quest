# VimQuest 設計仕様

作成日: 2026-08-18

## 1. 概要

Vim Adventures に着想を得た、ブラウザで動く Vim 学習ゲームである。
本物の Vim と同じ意味論で動くテキストバッファをゲーム盤とし、
ステージクリア型のパズルを通じて移動コマンドから基本編集コマンドまでを段階的に習得させる。

プロジェクト名は仮に `VimQuest` とする。

### 設計の中心にある判断

ゲーム盤を「タイルマップの迷路」ではなく「本物のテキストバッファ」とした。
今回のスコープに編集コマンド (`d` `c` `y` `p`) が含まれる以上、
学習価値の大半は意味論が本物であることに由来する。
見た目の地味さは演出で埋められるが、意味論の破綻は演出では埋められない。

## 2. スコープ

### 含むもの

- 移動コマンド: `h j k l` / `w W b B e E ge` / `0 ^ $` / `gg G {n}G` / `f F t T ; ,` / `{ }`
- 編集コマンド: `x` / `d` `c` `y` + モーション / `dd` `cc` `yy` / `p` `P` / `i a I A o O` / `r` / `u`
- 前置回数 `[count]`
- 全 18 ステージのカリキュラム
- ステージ選択画面、進行の永続化、キーストロークによる ☆ 評価

### 含まないもの（非目標）

- ビジュアルモード (`v` `V`)
- 検索 (`/` `?` `n` `N`)
- `.` リピート、マクロ (`q` `@`)、名前付きレジスタ、マーク
- テキストオブジェクト (`iw` `ap` 等)
- Ex コマンド (`:w` `:s` 等)
- ステージエディタ、サーバー連携、アカウント、ランキング

これらは将来の拡張余地として設計を妨げない形にしておくが、初回では作らない。

## 3. アーキテクチャ

依存は一方向にのみ流れる。

```
ui  →  game  →  stages
                  ↓
                core   （どこにも依存しない）
```

### 3.1 core — Vim エンジン

DOM に一切依存しない純粋 TypeScript。中心は 1 つの状態と 1 つの関数である。

```ts
type Cursor = { row: number; col: number }

type Register = { text: string[]; linewise: boolean }

type Pending =
  | { kind: 'operator'; op: 'd' | 'c' | 'y'; count: number }
  | { kind: 'charSearch'; motion: 'f' | 'F' | 't' | 'T'; count: number; op?: 'd' | 'c' | 'y' }
  | { kind: 'replace' }        // r の後、置換文字待ち
  | { kind: 'g'; count: number; op?: 'd' | 'c' | 'y' }   // g の後、gg / ge 待ち

type EditorState = {
  lines: string[]
  cursor: Cursor
  mode: 'normal' | 'insert'
  register: Register
  pending: Pending | null
  count: number | null         // 入力途中の数値プレフィックス
  desiredCol: number           // j / k で保持する望ましい列
  undoStack: Snapshot[]
}

type Snapshot = { lines: string[]; cursor: Cursor }

applyKey(state: EditorState, key: string): EditorState   // 純粋関数
```

ファイル分割:

| ファイル | 責務 |
|---|---|
| `types.ts` | 上記の型定義 |
| `keys.ts` | キー表記の解析 (`parseKeys`)。core とステージ層の共通語彙 |
| `buffer.ts` | 行配列に対する挿入・削除・分割・結合。カーソルを持たない |
| `motions.ts` | `(lines, cursor, count) => MotionResult` の集合 |
| `operators.ts` | オペレータとモーションの合成、`x` `p` `P` `r` `u` |
| `keymap.ts` | キー入力列を解釈する状態機械。ペンディング管理 |
| `editor.ts` | 上記を束ね `applyKey` を公開する |

モーションは移動先の座標だけでなく、オペレータと合成する際の性質を返す。

```ts
type MotionResult = {
  cursor: Cursor
  kind: 'exclusive' | 'inclusive' | 'linewise'
}
```

### 3.2 stages — ステージ定義

ロジックを持たず、JSON データとローダのみを置く。

### 3.3 game — ゲーム進行

ステージのロード、ゴール判定、キーストローク計数、☆ 評価、進行の永続化。
`core` の薄いラッパに徹し、Vim の意味論をここに書かない。

### 3.4 ui — 描画と入力

グリッド描画、ステージ選択画面、クリア演出、キーボードイベントの受け取り。
ゲームのルールを一切持たない。

## 4. Vim 意味論の細則

実装時の曖昧さを消すため、実 Vim に合わせる細部を明示する。
ここに書かれた挙動は全てユニットテストで固定する。

### 4.1 モーションの性質

| モーション | 性質 | 備考 |
|---|---|---|
| `h` `l` | exclusive | 行をまたがない |
| `j` `k` | linewise | `desiredCol` を記憶し、短い行では行末に丸める |
| `w` `W` | exclusive | 次の単語の先頭へ |
| `b` `B` | exclusive | 前の単語の先頭へ |
| `e` `E` | inclusive | 単語の末尾へ |
| `ge` | inclusive | 前の単語の末尾へ |
| `0` | exclusive | 行頭へ |
| `^` | exclusive | 行の最初の非空白へ |
| `$` | inclusive | 行末へ |
| `gg` `G` `{n}G` | linewise | 移動後は行の最初の非空白へ |
| `f` | inclusive | 対象文字そのものまで |
| `t` | inclusive | 対象文字の手前まで |
| `F` | exclusive | 後方の対象文字そのものまで |
| `T` | exclusive | 後方の対象文字の次まで |
| `;` `,` | 直前の `f F t T` に従う | `,` は逆方向 |
| `{` `}` | exclusive | 空行を段落境界とする。着地列は常に 0 |

「単語」の定義は Vim に従う。
`w` は英数字とアンダースコアの連なり、または記号の連なりを 1 単語とする。
`W` は空白で区切られた塊を 1 単語とする。

### 4.2 オペレータとの合成

- exclusive モーションとの合成では、開始位置から移動先の直前までを対象とする。
- inclusive モーションとの合成では、移動先の文字を含む。
- linewise モーションとの合成では、行単位で対象とする。
- 後方への inclusive モーション（`ge`）とオペレータの合成は、
  実 Vim の挙動が直感に反するうえカリキュラムで使わないため、exclusive と同じ扱いにする。
- `dd` `cc` `yy` はオペレータの重ね押しで linewise 動作となる。
- `dw` が行末を越えないという Vim の特例に従う。カーソルが行の最後の単語上にあるとき、
  `dw` は行末までを削除し、次の行と結合しない。
- `cw` の特例に従う。カーソルが非空白文字の上にあるとき、`cw` は
  「現在の単語の末尾まで」を inclusive で対象とする。
  既に単語の末尾にいる場合はその 1 文字だけが対象になる。
  `ce` と混同しないこと。`e` は必ず 1 つ以上進むため、
  1 文字の単語では次の単語の末尾まで巻き込んでしまう。
- `cc` は行の内容を消して挿入モードに入る。行そのものは削除しない。
- `dd` で最終行を削除した結果バッファが空になる場合、空文字列 1 行を残す。

### 4.3 レジスタとペースト

- 無名レジスタを 1 つだけ持つ。名前付きレジスタは実装しない。
- `d` `c` `x` `y` は全て無名レジスタを上書きする。
- charwise の場合、`p` はカーソルの次の位置へ、`P` はカーソル位置へ挿入する。
- linewise の場合、`p` は次の行へ、`P` は前の行へ挿入し、
  カーソルは挿入した先頭行の最初の非空白へ移る。

### 4.4 挿入モード

- 印字可能文字はカーソル位置に挿入する。
- `Escape` でノーマルモードへ戻り、カーソルを 1 つ左へ動かす（行頭では動かさない）。
- `Backspace` はカーソル直前の 1 文字を削除する。行頭では前の行と結合する。
- `Enter` は行を分割する。
- `i` はカーソル位置、`a` はカーソルの次の位置、`I` は行の最初の非空白、`A` は行末から開始する。
- `o` は下に、`O` は上に空行を作って挿入モードへ入る。

### 4.5 アンドゥ

- アンドゥの 1 単位は「ノーマルモードの 1 コマンド」
  または「挿入モードの開始から `Escape` まで」とする。
- 実装はスナップショット方式とする。バッファサイズが小さいため差分管理は不要である。
- `u` はスナップショットを 1 つ戻す。リドゥ (`Ctrl-r`) は実装しない。

### 4.6 前置回数

- `3w` と `d3w` と `3dw` を全て受け付ける。`3dw` は `d3w` と等価とする。
- `0` は回数入力中でなければ行頭移動として扱う。回数入力中なら数字として扱う。

### 4.7 不正なキー列

未定義のキー列を受け取った場合、ペンディング状態と入力中の回数を破棄して黙って無視する。
エラーを表示しない。これは実 Vim の挙動と一致する。

## 5. ステージ定義

```ts
type Stage = {
  id: string
  title: string
  lesson: string           // 教えるコマンドの説明文
  allowedKeys: string      // このステージで使えるキーのキー表記
  buffer: string[]         // 初期バッファ
  cursor: [number, number] // 初期カーソル [row, col]
  goal:
    | { type: 'collect';   targets: [number, number][] }
    | { type: 'transform'; expected: string[] }
  solution: string         // 想定解のキー表記。テストと par 算出に使う
}
```

### 5.1 キー表記

`allowedKeys` と `solution` は「1 文字 = 1 キー」の文字列とする。
印字できないキーは山括弧のトークンで表す。

| トークン | キー |
|---|---|
| `<Esc>` | `Escape` |
| `<CR>` | `Enter` |
| `<BS>` | `Backspace` |
| `<Space>` | 空白文字 |
| `<lt>` | `<` |

`parseKeys(notation: string): string[]` がこの表記をキー配列へ展開する。
JSON にキーを 1 つずつ並べるより読み書きしやすく、ステージ作成の負担が下がる。

### 5.2 par の導出

`par` はデータとして持たず、`parseKeys(solution).length` から導出する。
二重管理を避けるためである。

ゴールは 2 種類のみとする。

- **collect**: 指定された全座標をカーソルが通過したらクリア。移動レッスン用。順不同でよい。
  初期カーソル位置をターゲットに含めてはならない。ローダの検証項目とする。
- **transform**: バッファが `expected` と完全一致したらクリア。編集レッスン用。

判定は毎キー入力後に実行する。
`transform` はモードを問わず判定する。挿入モード中に一致した時点でクリアとする。

`allowedKeys` に含まれないキーは弾き、
「このステージでは `w` はまだ使わない」という趣旨のメッセージをフラッシュ表示する。

**`allowedKeys` の検査は、ノーマルモードかつリテラル文字待ちでないときのみ行う。**
挿入モード中の入力、`f F t T` の対象文字、`r` の置換文字は検査対象外とし、
任意の印字可能文字を受け付ける。
そうしなければ挿入モードで文字が打てず、`f` の対象文字も指定できない。

キーストローク数は**キー押下 1 回を 1 と数える**。
`dw` は 2、`3dw` は 4 と数える。
`allowedKeys` で弾かれたキーは加算しない。

☆☆☆ は「想定した最短手順と同等以下で解いた」ことを意味する。
ステージ作成時は `solution` が実際に最短に近いことを確認する。

## 6. カリキュラム

全 18 ステージ。

| # | 教えるもの | 種別 |
|---|---|---|
| 1 | `h j k l` | collect |
| 2 | `w b` 単語移動 | collect |
| 3 | `e ge` 単語末 | collect |
| 4 | `0 ^ $` 行内ジャンプ | collect |
| 5 | `gg G {n}G` 行ジャンプ | collect |
| 6 | `f F t T ; ,` 文字検索移動 | collect |
| 7 | `{ }` 段落移動 | collect |
| 8 | 移動の総合（`W B E` もここで解放） | collect |
| 9 | `x` 削除 | transform |
| 10 | `dw d$ dd` オペレータ + モーション | transform |
| 11 | `i a I A o O` 挿入モード | transform |
| 12 | `cw c$ cc` チェンジ | transform |
| 13 | `yy y` + モーション / `p P` ヤンクとペースト | transform |
| 14 | `u` アンドゥ / `r` 置換 | transform |
| 15 | `[count]` 前置回数 | transform |
| 16 | 総合 1 | transform |
| 17 | 総合 2 | transform |
| 18 | 総合 3 | transform |

ステージ 10 が構成上の山場である。
ここまでにモーションを一通り体に入れてあるため、
`d` を覚えた瞬間に組み合わせが一気に開くという体験を作る。

一度解放されたコマンドは以降のステージでも使える。
`allowedKeys` は「そのステージまでに教えたコマンドの累積」として定義する。
ただし総合ステージ以外では、狙ったコマンドを使わせるために
バッファ構成と `par` で誘導する。

## 7. game 層の仕様

### 7.1 スコア

| 条件 | 評価 |
|---|---|
| キーストローク数 ≤ par | ☆☆☆ |
| キーストローク数 ≤ par × 1.5 | ☆☆ |
| クリアのみ | ☆ |

### 7.2 進行の永続化

`localStorage` のキー `vimquest:progress` に以下を保存する。

```ts
type Progress = {
  version: 1
  cleared: Record<string, { stars: number; bestKeystrokes: number }>
}
```

ステージ N をクリアするとステージ N+1 が解放される。
`localStorage` が使えない場合は保存を諦めて続行する。ゲーム自体は動く。

## 8. ui 層の仕様

- 中央に等幅フォントでバッファを描画する。1 文字 1 セル。
- カーソルはノーマルモードでブロック、挿入モードで縦棒とし、色も変える。
- `collect` のターゲットはセル背景を発光させ、踏むと弾けて消える。
- 上部にステージ名とレッスン文を表示する。
- 下部にモード表示、キーストローク数 / par、押したキー列の履歴を表示する。
  この履歴が「自分が何を押したか」の振り返りとなり、無駄打ちの自覚につながる。
- クリア時に ☆ 評価を表示し、次のステージへ進むか `R` でリトライする。
- ステージ選択はグリッド表示。未解放のステージはロック表示とする。
- 配色は gruvbox 風のダークテーマとする。

キーボードイベントは `keydown` で受け、ブラウザの既定動作を抑止する。
ただし `Ctrl` `Alt` `Meta` を伴う入力は透過させ、ブラウザのショートカットを潰さない。

## 9. テスト戦略

### 9.1 core のユニットテスト

Vitest でテーブル駆動テストを書く。
「初期バッファ + 初期カーソル + キー列 → 期待されるバッファとカーソルとモード」の表を並べる。
これが実質の仕様書となる。第 4 節に挙げた細則を全て網羅する。

実装は TDD で進める。テストを先に書き、失敗を確認してから実装する。

### 9.2 ステージの解けることの自動検証

各ステージの `solution` キー列をゲームのセッションに流し込み、以下を検証する。

- ゴール判定が真になる
- 消費キー数が `par` と一致する
- `allowedKeys` に弾かれたキーが 1 つもない

3 番目は「`solution` の全キーが許可されている」ことの検査である。
セッションは弾いたキーを数えるので、その累計が 0 であることを見れば足りる。
`allowedKeys` の記述漏れはこれで確実に落ちる。

これによりステージ追加・変更時の破綻が即座に検出される。
ステージデータが増えても品質が保たれる仕組みとして、これが最も費用対効果が高い。

### 9.3 UI

手動確認とする。自動化しない。

## 10. エラー処理

| 事象 | 扱い |
|---|---|
| 未定義のキー列 | ペンディングと回数を破棄して無視。表示なし |
| 許可されていないキー | 弾いてフラッシュ表示。キーストロークに加算しない |
| `localStorage` の読み書き失敗 | 保存を諦めて続行 |
| ステージ JSON の不正 | ロード時に検証し、該当ステージをロック表示 |

## 12. 技術スタック

- Vite（開発サーバとビルド）
- TypeScript（strict モード）
- Vitest（ユニットテスト）
- UI フレームワークは使わない。素の DOM 操作で描画する

最終成果物は静的ファイルへビルドでき、任意の静的ホスティングに置ける。
